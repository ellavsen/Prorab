# Мониторинг рыночных цен на материалы и работы

Статус: проект (draft). Область: сбор, нормализация, агрегация и выдача
рыночных цен для (а) подсказки цены при составлении сметы (статус
`assumed_catalog`, см. [ai-contract.md](ai-contract.md) §2) и (б) еженедельного
публичного дайджеста. Денежные конвенции — по [money.md](money.md):
в хранилище копейки целыми числами, float в деньгах запрещён.

Целевой запрос: `(позиция="цемент М500", регион="Крым", сейчас)` →
`{медиана, p25–p75, N независимых источников, свежесть, база оценки}`.

---

## 0. Принципы, из которых всё следует

1. **Факт цены — атом системы.** Всё остальное (агрегаты, дайджест,
   подсказки) — детерминированные функции над множеством фактов.
   Факты append-only; ошибка исправляется сменой статуса, не правкой.
2. **Сырьё не храним.** Из источника извлекается только структурированный
   факт + ссылка на публикацию. Текст сообщения, файл прайса, имя автора —
   отбрасываются на этапе ингеста и не попадают ни в БД, ни в логи.
3. **Никаких платных API и тяжёлого железа.** Весь пайплайн — Python +
   SQLite, работает на том же хосте, что и бот. Эмбеддинги — опциональный
   офлайн-шаг на CPU, не в пути запроса.
4. **Честность оценки важнее её наличия.** Ниже порога данных сервис говорит
   «недостаточно данных», а не выдаёт число.

## 1. Модель данных факта цены

### 1.1. Поля

| Поле | Тип | Смысл |
|---|---|---|
| `id` | INTEGER PK | |
| `item_id` | FK → `item` | каноническая позиция справочника |
| `region_id` | FK → `region` | лист иерархии регионов, где действует цена |
| `price_kop` | INTEGER | цена в копейках **за базовую единицу позиции** (после конвертации §3) |
| `orig_price_kop` | INTEGER | цена как опубликована |
| `orig_unit` | TEXT | единица как опубликована (`мешок_50кг`) |
| `conv_exact` | INTEGER (bool) | конвертация точная (фасовка) или приближённая (через плотность) |
| `source_id` | FK → `source` | источник |
| `doc_id` | FK → `document` NULL | документ-носитель (прайс/пост); NULL для крауда |
| `contributor_key` | TEXT NULL | псевдоним пользователя крауда, HMAC (см. 1.3) |
| `url` | TEXT NULL | ссылка на публикацию (пост/прайс); у крауда NULL |
| `observed_at` | TEXT (ISO date) | дата публикации цены |
| `ingested_at` | TEXT (ISO datetime) | когда принят системой |
| `status` | TEXT | `active / duplicate / quarantined / source_disabled` |
| `status_reason` | TEXT NULL | машинный код причины (`iqr_outlier`, `doc_dup`, …) |
| `fingerprint` | TEXT | ключ дедупликации (см. 1.2) |

Раздельные `price_kop` / `orig_*` — чтобы конвертация была пересчитываемой:
при исправлении коэффициента фасовки факт нормализуется заново из оригинала.

### 1.2. Ключ уникальности

Естественного ключа у «цены в канале» нет, поэтому ключ — синтетический
отпечаток факта:

```
fingerprint = sha256(item_id | region_id | price_kop | orig_unit |
                     observed_week | origin)
origin = doc_fingerprint            # для прайсов и каналов
       | contributor_key            # для крауда
```

`UNIQUE(fingerprint)`: тот же источник, повторивший ту же цену на той же
неделе, — это один факт (повторный ингест идемпотентен). Та же цена от
**другого** независимого источника — другой fingerprint, законный второй факт.
Дедупликация растиражированных прайсов — отдельный механизм (§4), потому что
там `origin` разный, а содержимое одно.

### 1.3. Краудсорсинг без персональных данных

Для защиты от накрутки нужна связь фактов одного автора, но хранить
`tg_user_id` нельзя. Решение — односторонний псевдоним:

```
contributor_key = HMAC-SHA256(K, tg_user_id)[:16]
```

- Секрет `K` живёт только в env процесса-ингестора, в БД не попадает.
- В БД нет ни `user_id`, ни username, ни имени — обратное восстановление
  без `K` невозможно.
- **Криптографическое стирание:** удаление/ротация `K` мгновенно и
  необратимо анонимизирует всю историю craуд-фактов разом (репутационные
  веса при этом обнуляются — осознанная цена).
- Псевдоним используется только внутри анти-абьюза (§5); наружу — никогда.

## 2. Нормализация названий

«цемент М500», «ЦЕМ II 42.5», «цемент пятисотый», «м500 мешок 50 кг» →
одна позиция каталога.

### 2.1. Модель каталога

Позиция — не строка, а структура: `item = (категория, вид, атрибуты)`,
где атрибуты — марка/класс, фасовка выносится в единицы (§3). Соответствия
старых и новых маркировок (М500 ≈ ЦЕМ I/II 42.5) — это **алиасы одной
позиции**, зафиксированные человеком в справочнике, а не догадка матчера.

### 2.2. Каскад сопоставления (дёшево → дорого)

| Ступень | Механизм | Стоимость | Доля трафика (ожидание) |
|---|---|---|---|
| T0 | точное совпадение нормализованной строки с `item_alias` (lowercase, ё→е, без пунктуации, токены отсортированы, вычленены фасовка и числа) | O(1), индекс | ~70% после прогрева |
| T1 | правила-токены: словарь переписываний («пятисотый»→«м500», «портланд»→«цемент», латиница↔кириллица M/М, B/В), затем снова T0 | микросекунды | +15% |
| T2 | нечёткое сопоставление RapidFuzz (token_set_ratio) по алиасам той же категории; порог ≥ 90 — автопривязка, 75–90 — в очередь модерации с кандидатами | миллисекунды, CPU | +10% |
| T3 (опция) | локальные эмбеддинги: квантованная маленькая модель (класс rubert-tiny2 / multilingual-e5-small, ONNX int8) + sqlite-vec; только офлайн-батчем по остаткам очереди, никогда в пути запроса | секунды/батч, CPU | хвост |
| T4 | модерация человеком в боте (одна кнопка «это цемент М500?») | | остаток |

**Ключевое свойство — самообучение справочника:** любое решение T2–T4
записывается новым алиасом, и та же формулировка в следующий раз ловится
на T0. Система дрейфует к «почти всё — точное совпадение».

### 2.3. Почему так, а не «эмбеддинги для всего»

- Номенклатура конечна и головаста: сотни позиций, тысячи формулировок —
  словарь + fuzzy покрывают её детерминированно, отлаживаемо и бесплатно.
- Эмбеддинги на слабом CPU дают латентность и невоспроизводимость решений;
  как офлайн-подсказчик кандидатов для модерации они полезны, как арбитр —
  нет. Порог автопривязки высокий, потому что цена ошибки — грязный агрегат.
- Ошибка матчинга исправима: факт хранит `orig_*`, перепривязка позиции —
  UPDATE `item_id` + пересчёт затронутых агрегатов.

## 3. Нормализация единиц

У каждой позиции — **базовая единица** (`item.base_unit`): цемент → тонна,
кабель → м_п, работа — её естественная единица (м², точка). Все `price_kop`
приведены к ней.

Коэффициенты — в таблице `unit_conversion`, двух видов:

1. **Точные (фасовка):** `мешок_50кг → т = 1/20`. Хранятся рациональной
   парой `factor_num / factor_den` (INTEGER), пересчёт цены — целочисленный,
   без float: `price_kop(база) = orig_price_kop × den / num` с банковской
   проверкой делимости и округлением HALF_UP до копейки (режим — как в
   money.md). Привязка: к позиции (`item_id`) или к категории
   (`category_id`), позиция важнее категории.
2. **Приближённые (плотность):** `кг ↔ м³` через плотность класса материала
   (цемент навалом ~1300 кг/м³). Факт, прошедший такую конвертацию, получает
   `conv_exact = 0` и половинный вес в агрегате (§5). Между массой и объёмом
   **без явно заданной плотности не конвертируем вообще** — факт остаётся
   в очереди модерации.

Справочник конвертаций пополняется так же, как алиасы: неизвестная фасовка →
модерация → новая строка `unit_conversion`.

## 4. Дедупликация: пять каналов ≠ пять источников

Три уровня, от дешёвого к умному:

1. **Документ.** Каждый прайс/пост при ингесте получает
   `doc_fingerprint = sha256(канонизированное множество строк (item, unit,
   price))` — не байты файла, а содержимое, поэтому один прайс в XLSX и
   его перепечатка постом дают один отпечаток. Повторный `doc_fingerprint`
   от другого источника → факты создаются со `status='duplicate'` и ссылкой
   `dup_of_doc`; в агрегат не идут, но связь источников фиксируется.
2. **Корреляция источников.** Ночной джоб считает по парам источников долю
   совпадающих фактов (item, price, неделя) за 90 дней. Пары с Жаккаром
   ≥ 0.6 попадают в `source_edge`; связные компоненты — **кластеры
   источников** (`source.cluster_id`). Кластер = «одна рука». Пять каналов,
   тиражирующих один прайс частями и с задержкой, склеиваются здесь, даже
   когда отпечатки документов различны.
3. **Счёт независимости.** Везде, где нужна «независимость» (порог показа,
   N в выдаче), считается `COUNT(DISTINCT cluster_id)`, а не число
   источников. Краудсорсинг: один `contributor_key` — свой одноэлементный
   кластер, и его повторные подтверждения той же позиции учитываются
   не чаще раза в 7 дней (fingerprint §1.2 это уже обеспечивает).

## 5. Отсев выбросов и защита от манипуляции

### 5.1. Конвейер фильтров (порядок важен)

```
факт → [жёсткие пределы] → [робастный выброс] → [вес источника] → агрегат
```

1. **Жёсткие пределы вменяемости** на категорию (цемент: 3 000–30 000 ₽/т,
   задаются в каталоге): вне — `quarantined/sanity`, человек посмотрит.
   Ловит ошибки единиц («350 ₽ за тонну» = цена мешка).
2. **Робастный выброс.** Внутри (item, region, окно 30 дн): при n ≥ 8 —
   границы `[Q1 − 1.5·IQR, Q3 + 1.5·IQR]`; при n < 8 — отклонение от
   медианы ближайшего уровня, где данных хватает (регион↑ или окно 90 дн),
   больше чем в 1.6 раза → `quarantined/outlier`. Карантин — не удаление:
   если за 14 дней рядом появляются подтверждающие независимые факты
   (рынок реально прыгнул), карантинные факты реабилитируются пересчётом.
3. **Вес источника (репутация).** `source.weight ∈ [0.1, 1.0]`:
   - старт: прайс-листы 0.7; крауд-новичок 0.3 первые 30 дней, затем 0.6;
     tg-канал 0.4;
   - +0.05 за факт, попавший в итоговый IQR-интервал (согласие с рынком),
     −0.1 за карантин, −0.2 за участие в дубль-кластере; клип в границы;
   - вес кластера = максимум по кластеру (не сумма — тираж не добавляет веса);
   - `conv_exact = 0` → вес факта ×0.5.

### 5.2. Анти-накрутка крауда (сценарий «поставщик рисует себе рынок»)

- Квоты: с одного `contributor_key` в агрегат входит ≤ 1 факт на
  (item, region) в 7 дней и ≤ 10 фактов суммарно в день; остальное —
  `quarantined/velocity`.
- Новые ключи 30 дней имеют вес 0.3 — свежесозданной пачкой аккаунтов
  медиану не сдвинуть, пока Σвесов честных источников выше.
- Медиана — **взвешенная** (по весам источников/кластеров): чтобы сдвинуть
  её, нужно превзойти суммарный вес независимых несогласных, а согласие
  с самим собой веса не приносит (кластеры).
- Сигнализация: страница (item, region), где за неделю доля фактов от
  одного кластера > 50% или медиана сдвинулась > 25% WoW при n < 10 —
  в очередь ручного просмотра, агрегат помечается `flagged` и в подсказке
  цены не используется (в дайджест не идёт).

### 5.3. Порог показа

Оценка публикуется, только если в базе оценки:

```
N_independent (кластеров) ≥ 3  И  Σ weight ≥ 2.0  И  свежесть ≤ окна
```

Иначе — эскалация базы (§6.2), а если и она не дала порога — честное
«недостаточно данных» (в боте: «мало данных по региону — введите цену
вручную», в дайджест позиция не попадает).

## 6. Агрегаты

### 6.1. Что храним

Материализованная таблица `price_agg` — по одной строке на
(item, region, window ∈ {7, 30, 90}):

`median_kop` (взвешенная медиана), `p25_kop`, `p75_kop`, `n_facts`,
`n_independent`, `sum_weight`, `freshest_at`, `flagged`, `computed_at`.

Пересчёт двумя путями, оба — чистый SQL/Python над `price_fact`:

- **инкрементально**: после ингеста пересчитываются только затронутые
  (item, region) — на SQLite это миллисекунды;
- **ночной полный** прогон: скользящие окна «протухают» сами по себе,
  без событий, плюс пересчёт корреляций §4.2 и реабилитаций §5.1.

### 6.2. Малая выборка: лестница эскалации

Регионы — дерево: `населённый пункт → субъект → макрорегион → РФ`.
База оценки расширяется по фиксированной лестнице до достижения порога §5.3:

```
(регион, 7д) → (регион, 30д) → (регион, 90д) →
(макрорегион, 30д) → (макрорегион, 90д) → (РФ, 90д) → нет оценки
```

Правила честности: уровни не смешиваются (никаких «добить крымскую выборку
московскими фактами»), а выдача всегда несёт `basis = {region_level,
window}` — бот показывает «медиана по Югу РФ за 30 дней», если до Крыма
данных не хватило. Дайджест публикует только уровни `регион, 7д/30д`.

### 6.3. Контракт выдачи (подсказка цены в смете)

```
get_price(item_id, region_id) →
  { median_kop, p25_kop, p75_kop,
    n_independent, freshest_at,
    basis: {region_level, window} }   | «нет данных»
```

Потребитель — пост-процессор из ai-contract.md: подставляет `median_kop` со
статусом `assumed_catalog`, в карточке подтверждения показывает разброс и
базу. Выбор пользователя (принял/поправил) возвращается в систему двумя
событиями: подтверждение = новый крауд-факт, правка = крауд-факт с его ценой
+ сигнал метрике качества (§7).

## 7. Метрики качества сервиса

Главный источник правды — уже существующая петля подтверждения смет: каждая
подсказанная цена либо принимается, либо правится, и это логируется как
событие (без текстов и без user_id — только item, region, suggested,
final, флаг принятия).

| Метрика | Определение | Целевой ориентир |
|---|---|---|
| Acceptance rate | доля `assumed_catalog`-цен, принятых без правки | > 60% |
| Median correction | медиана `abs(final − suggested)/suggested` по правкам | < 15% |
| Coverage | доля запросов подсказки, где порог §5.3 достигнут (на любом уровне лестницы) | > 80%, из них ≥ 50% на уровне «регион» |
| Калибровка разброса | доля пользовательских финальных цен, попавших в показанный [p25, p75] | ~50% (интервал честный: сильно больше — интервал раздут, сильно меньше — занижен) |
| Freshness | медианный возраст фактов в базе выдачи | ≤ 14 дней |
| Manipulation drill | офлайн-тест: синтетическая атака (пачка фактов одного кластера) не сдвигает медиану > 5% и попадает в `flagged` | 100% прогонов |
| Дайджест | подписки/удержание | вторично, не влияет на пайплайн |

Acceptance и correction считаются в разрезе (категория × уровень базы) —
деградация «подсказки по РФ принимают вдвое реже» видна сразу и говорит,
где добирать источники.

## 8. Юридические и репутационные риски

| Риск | Минимизация на уровне дизайна |
|---|---|
| **Персональные данные** | В БД нет ни текстов, ни имён, ни id — только факт цены и URL публикации (принцип §0.2, схема §1 это физически не позволяет: колонок нет). Псевдоним крауда — HMAC с внешним секретом; ротация секрета = криптографическое стирание всей истории (§1.3). Логи ингеста не содержат payload источников. |
| **Авторские/смежные права на прайс-листы** | Отдельная цена — факт, не объект права; система хранит извлечённые факты + ссылку, а не копии документов (документ живёт только как отпечаток-хеш). Не делаем полного «зеркала» чьей-либо базы: с одного источника берутся только позиции, присутствующие в нашем каталоге. Сканер уважает robots.txt, ходит с честным User-Agent и щадящим rate limit. |
| **Telegram-каналы** | Только публичные, только явно добавленные пользователем, чтение через официальный API. Канал — это `source` со всеми правами обычного источника: запрос владельца на удаление → `enabled = 0` + вычистка `url` из его фактов. |
| **Kill-switch (жёсткое требование)** | `source.enabled = 0` — единственная настройка: ингест останавливается немедленно, ближайший пересчёт помечает все факты источника `source_disabled` и исключает их из всех агрегатов. Никаких каскадных ручных операций. |
| **Обвинение в манипулировании рынком / диффамации** | Публикуем только агрегаты (медиана/разброс/N), никогда — сравнение конкретных поставщиков и ярлыки «дорого/дёшево». Методология — публичная страница (окна, пороги, отсев). Дисклеймер в каждом дайджесте и подсказке: справочная информация, не оферта и не рекомендация цены. |
| **Антимонопольный ракурс** | Дайджест — агрегированная историческая статистика с задержкой (7-дневное окно), не канал координации текущих цен между поставщиками; матрицы «поставщик × цена» не существует даже внутри системы (источник факта наружу не раскрывается). |
| **Ошибочная подсказка → испорченная смета** | Подсказка всегда помечена как предположение, требует явного подтверждения (контракт ai-contract.md), несёт разброс и базу оценки; ниже порога — не показывается вовсе (§5.3). |

## 9. DDL (SQLite)

```sql
-- Справочники ---------------------------------------------------------

CREATE TABLE category (
    id        INTEGER PRIMARY KEY,
    name      TEXT NOT NULL UNIQUE,
    min_kop   INTEGER,              -- жёсткие пределы вменяемости (§5.1)
    max_kop   INTEGER
);

CREATE TABLE item (
    id          INTEGER PRIMARY KEY,
    category_id INTEGER NOT NULL REFERENCES category(id),
    kind        TEXT NOT NULL,      -- 'material' | 'work'
    name        TEXT NOT NULL,      -- каноническое имя: 'Цемент М500 (ЦЕМ I 42.5)'
    attrs       TEXT,               -- JSON атрибутов: {"grade":"м500"}
    base_unit   TEXT NOT NULL,      -- 'т', 'м2', 'точка', ...
    UNIQUE (category_id, name)
);

CREATE TABLE item_alias (
    alias_norm  TEXT PRIMARY KEY,   -- нормализованная строка (§2.2 T0)
    item_id     INTEGER NOT NULL REFERENCES item(id),
    origin      TEXT NOT NULL       -- 'seed' | 'auto_fuzzy' | 'moderated'
);

CREATE TABLE unit_conversion (
    id          INTEGER PRIMARY KEY,
    item_id     INTEGER REFERENCES item(id),      -- NULL = на категорию
    category_id INTEGER REFERENCES category(id),
    from_unit   TEXT NOT NULL,                    -- 'мешок_50кг'
    factor_num  INTEGER NOT NULL,                 -- from = num/den × base
    factor_den  INTEGER NOT NULL,
    exact       INTEGER NOT NULL DEFAULT 1,       -- 0 = через плотность (§3)
    CHECK (item_id IS NOT NULL OR category_id IS NOT NULL)
);

CREATE TABLE region (
    id        INTEGER PRIMARY KEY,
    parent_id INTEGER REFERENCES region(id),      -- дерево: нас.пункт→субъект→макро→РФ
    name      TEXT NOT NULL,
    level     INTEGER NOT NULL                    -- 0=РФ .. 3=нас.пункт
);

-- Источники ------------------------------------------------------------

CREATE TABLE source (
    id          INTEGER PRIMARY KEY,
    type        TEXT NOT NULL,      -- 'crowd' | 'pricelist' | 'tg_channel'
    title       TEXT NOT NULL,      -- 'прайс stroybaza.example' / 'crowd'
    url         TEXT,               -- корень источника; у crowd NULL
    enabled     INTEGER NOT NULL DEFAULT 1,   -- kill-switch (§8)
    weight      REAL NOT NULL DEFAULT 0.5,    -- репутация (§5.1)
    cluster_id  INTEGER,            -- компонента корреляции (§4.2)
    added_by    TEXT                -- 'operator' | 'user_request'
);

CREATE TABLE source_edge (          -- рёбра корреляции источников (§4.2)
    src_a     INTEGER NOT NULL REFERENCES source(id),
    src_b     INTEGER NOT NULL REFERENCES source(id),
    jaccard   REAL NOT NULL,
    computed_at TEXT NOT NULL,
    PRIMARY KEY (src_a, src_b)
);

CREATE TABLE document (             -- носитель, хранится ТОЛЬКО отпечаток (§4.1)
    id              INTEGER PRIMARY KEY,
    source_id       INTEGER NOT NULL REFERENCES source(id),
    doc_fingerprint TEXT NOT NULL,
    url             TEXT,
    published_at    TEXT,
    dup_of_doc      INTEGER REFERENCES document(id)
);
CREATE INDEX idx_document_fp ON document(doc_fingerprint);

-- Факты ----------------------------------------------------------------

CREATE TABLE price_fact (
    id              INTEGER PRIMARY KEY,
    item_id         INTEGER NOT NULL REFERENCES item(id),
    region_id       INTEGER NOT NULL REFERENCES region(id),
    price_kop       INTEGER NOT NULL CHECK (price_kop >= 0),
    orig_price_kop  INTEGER NOT NULL,
    orig_unit       TEXT NOT NULL,
    conv_exact      INTEGER NOT NULL DEFAULT 1,
    source_id       INTEGER NOT NULL REFERENCES source(id),
    doc_id          INTEGER REFERENCES document(id),
    contributor_key TEXT,                         -- HMAC-псевдоним (§1.3)
    url             TEXT,
    observed_at     TEXT NOT NULL,                -- ISO date
    ingested_at     TEXT NOT NULL,
    status          TEXT NOT NULL DEFAULT 'active',
        -- 'active'|'duplicate'|'quarantined'|'source_disabled'
    status_reason   TEXT,
    fingerprint     TEXT NOT NULL UNIQUE          -- (§1.2)
);
CREATE INDEX idx_fact_lookup ON price_fact(item_id, region_id, observed_at)
    WHERE status = 'active';

-- Агрегаты и обвязка ----------------------------------------------------

CREATE TABLE price_agg (
    item_id       INTEGER NOT NULL REFERENCES item(id),
    region_id     INTEGER NOT NULL REFERENCES region(id),
    window_days   INTEGER NOT NULL,               -- 7 | 30 | 90
    median_kop    INTEGER NOT NULL,
    p25_kop       INTEGER NOT NULL,
    p75_kop       INTEGER NOT NULL,
    n_facts       INTEGER NOT NULL,
    n_independent INTEGER NOT NULL,               -- DISTINCT cluster_id (§4.3)
    sum_weight    REAL NOT NULL,
    freshest_at   TEXT NOT NULL,
    flagged       INTEGER NOT NULL DEFAULT 0,     -- (§5.2)
    computed_at   TEXT NOT NULL,
    PRIMARY KEY (item_id, region_id, window_days)
);

CREATE TABLE moderation_queue (
    id          INTEGER PRIMARY KEY,
    kind        TEXT NOT NULL,   -- 'alias_match'|'unit_unknown'|'sanity'|'flagged_agg'
    payload     TEXT NOT NULL,   -- JSON: кандидаты, факт, контекст
    created_at  TEXT NOT NULL,
    resolved_at TEXT,
    resolution  TEXT             -- JSON решения; порождает alias/conversion/статус
);

-- Петля качества (§7): без текстов и без идентификаторов пользователя
CREATE TABLE suggestion_event (
    id            INTEGER PRIMARY KEY,
    item_id       INTEGER NOT NULL REFERENCES item(id),
    region_id     INTEGER NOT NULL REFERENCES region(id),
    suggested_kop INTEGER NOT NULL,
    basis_level   INTEGER NOT NULL,  -- уровень региона в лестнице (§6.2)
    basis_window  INTEGER NOT NULL,
    accepted      INTEGER NOT NULL,  -- 1 = принято без правки
    final_kop     INTEGER,           -- цена после правки (NULL если принято)
    created_at    TEXT NOT NULL
);
```

## 10. Пайплайн

```
        ┌─ crowd (бот: подтверждение/своя цена)
входы ──┼─ fetcher прайсов (HTML/XLSX, cron, rate-limit, robots.txt)
        └─ reader tg-каналов (официальный API, только явно добавленные)
                    │
                    ▼  (сырьё живёт только в памяти процесса)
 [1] ИЗВЛЕЧЕНИЕ    строки (raw_name, raw_unit, raw_price, url, date)
                    │        прайс/пост → doc_fingerprint → дубль? → duplicate
                    ▼
 [2] НОРМАЛИЗАЦИЯ  имя: каскад T0→T4 (§2)   единица: unit_conversion (§3)
                    │        не сматчилось → moderation_queue, факт ждёт
                    ▼
 [3] ФАКТ          сборка fingerprint, INSERT OR IGNORE (идемпотентно)
                    │
 [4] ФИЛЬТРЫ       пределы вменяемости → IQR/медианный тест → статус (§5.1)
                    │
 [5] АГРЕГАЦИЯ     инкрементальный пересчёт затронутых (item, region) (§6.1)
                    │
        ┌───────────┴───────────────┐
 [6] ВЫДАЧА                   [7] НОЧНОЙ БАТЧ
 get_price() с лестницей       полный пересчёт окон, корреляция
 эскалации (§6.2/6.3);         источников (§4.2), реабилитация
 еженедельный дайджест         карантина, обновление весов (§5.1),
 (только agg, только           сигнализация манипуляций (§5.2),
 регион 7/30д)                 экспорт метрик (§7)
```

Свойства пайплайна: каждый шаг идемпотентен (повторный прогон того же входа
не меняет состояние — гарантируется fingerprint-ами), факты append-only со
статусной машиной, все решения фильтров записаны в `status_reason` —
любой агрегат можно объяснить построчно.

## 11. Явно вне области

- Прогноз цен (только текущие/исторические агрегаты).
- Парсинг маркетплейсов и сайтов без прямых ссылок на прайс (правовой риск
  и хрупкость; добавляется отдельным решением, если появится).
- Автоматическая покупка/интеграция с поставщиками.
- Персональные рекомендации «где купить» (наружу не раскрываем источники —
  §8, антимонопольный ракурс).
