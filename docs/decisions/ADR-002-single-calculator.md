# ADR-002. Единственный вычислитель итогов — чистая функция домена

**Статус:** принято, Sprint 1.

**Контекст.** Итог считался четырьмя способами: `sum_line_with_tax()` в Python,
`func.sum((qty*price)*(1+float(TAX_RATE)))` в SQL, формула `=C*D*1.06` в строке
Excel и `=SUM(...)` по её результатам. На 10 000 случайных смет 72.1% расходились
между собой; на смете из двух строк сумма показанных строк не сходилась с
показанным «Итого» (159,16 + 265,27 = 424,43, а бот писал 424,42).

**Решение.** Вся денежная арифметика — в `smeta_core.calculate_estimate()`.
`/list`, `/estimates` и XLSX — потребители её результата. Денежные агрегаты в SQL
запрещены: `func.sum` по деньгам больше не встречается в проекте, что проверяет
тест `test_no_arithmetic_left_in_the_rendering_layer`. Формулы XLSX — не второй
вычислитель, а транскрипция той же схемы, паритет которой доказан тестами.

**Альтернативы.** Синхронизировать четыре пути дисциплиной — ровно это и не
сработало. Считать итог в SQL ради скорости — при сотнях строк выигрыша нет.

**Следствия.** Итог требует загрузки строк сметы; `/estimates` делает по запросу
на смету (их не больше пяти). Ставка наценки живёт в самой смете, поэтому её
изменение не переписывает историю — см. ADR-003.
