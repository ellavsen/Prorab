# ADR-011. Разбор справа, и отказ угадывать при неоднозначности

**Статус:** принято, Sprint 4.

**Контекст.** В строке «Наименование, количество, цена» запятая работает сразу
в трёх ролях: разделитель полей, десятичный разделитель и обычный символ внутри
наименования. В строительстве последнее — норма: «Гвозди 3,5 мм»,
«Труба 20х20х1,5», «Уголок 30, оцинкованный».

История вопроса в проекте:

- до Sprint 2 строка `Побелка, 150,5, 3000` **молча** читалась как количество
  150 и цена 5 — то есть смета получала неверные деньги без единого признака;
- Sprint 2 сделал отказ явным: «получено полей: 4, а нужно 3». Честно, но
  обычные наименования с запятыми стали неприемлемы;
- Sprint 4 должен был научить парсер их принимать.

**Решение.**

1. **Разбор справа.** `rsplit(",", 2)`: последние два поля — количество и цена,
   всё слева — наименование, **как напечатано**. `Гвозди 3,5 мм, 100, 20`
   разбирается верно, и имя не переписывается в «Гвозди 3.5 мм».
2. **Десятичная запятая** принимается там, где она однозначна: строго между
   цифрами и без пробелов (`150,5` — да, `100, 20` — нет).
3. Строка читается **обоими** способами. Если валиден один — берётся он. Если
   оба, но количество и цена совпадают, различие только в тексте имени, и
   берётся напечатанный вариант, без вопросов.
4. Если оба валидны и **деньги расходятся** — парсер поднимает `AmbiguousLine`
   с обоими прочтениями, а бот показывает их и спрашивает. Молча выбирать
   нельзя: это тот же класс поведения, из-за которого появились ADR-005 и
   ADR-006.

**Что оказалось не неоднозначным.** `Гвозди,100,20` без пробелов выглядит
двусмысленно, но слитое чтение даёт два поля вместо трёх, то есть недопустимо.
Выбора там нет, и переспрашивать не о чем.

**Альтернативы.** Требовать точку и отвергать запятую в числах — переучивание
пользователя под удобство парсера. Запретить запятые в наименованиях —
запрет на реальные названия материалов. Всегда предпочитать одно чтение —
возврат к молчаливому угадыванию.

**Следствия.** Неоднозначная строка хранится в `pending_line` того же черновика
(ADR-010), пока пользователь не выберет вариант. API и веб-демо отдают оба
прочтения в поле `readings`, а не превращают их в текст ошибки. При вводе
нескольких строк разом неоднозначные разбираются по одной; остальные
добавляются сразу.
