# ADR-008. API без состояния, деньги на проводе — строками

**Статус:** принято, Sprint 3.

**Контекст.** HTTP-слой — четвёртый потребитель ядра после бота, XLSX и демо.
Каждый предыдущий раз, когда деньги пересекали границу технологии, они теряли
копейки: `Numeric` в SQLite оказался REAL, `func.sum` считал во float, формула
Excel умножала на `1.06` в double. JSON — такая же граница: число в JSON это
IEEE-754 double, и `159.16` на той стороне становится `159.16000000000000369…`.

**Решение.**

1. **Деньги, количества и ставки передаются строками** (`"159.16"`, `"0.007"`).
   Pydantic сериализует `Decimal` строкой по умолчанию — на это и рассчитано.
   В OpenAPI они описаны как `type: string`, чтобы сгенерированный клиент не
   завёл `float`. Проверяется тестом `test_money_travels_as_strings`.
2. **API не хранит состояния.** Ни базы, ни сессий, ни `smeta_storage`. Вход —
   позиции и ставки, выход — итоги или файл. Публиковать такой сервис можно не
   думая: персональных данных в нём нет по построению.
3. **Границы значений в схемах не дублируются.** Их проверяет домен при
   создании `PositionData`. Второй набор проверок разошёлся бы с первым ровно
   так же, как расходились четыре вычислителя до Sprint 1.
4. **Отказ домена — это 422 с его же текстом.** `ValueError` из ядра
   превращается в `{"detail": "Количество: должно быть больше нуля"}`.
   Сообщение писалось для прораба и годится как ответ API без перевода.
5. **`openapi.json` лежит в репозитории** и сверяется в CI. Иначе об изменении
   публичного интерфейса первым узнаёт потребитель, а не автор.

**Альтернативы.** Числа в JSON с округлением на клиенте — это и есть второй
вычислитель. Целые копейки на проводе (`15916`) точны, но нечитаемы в примерах
и требуют от клиента знать масштаб каждого поля.

**Следствия.** Клиент обязан разбирать строки как десятичные, а не как `float`.
Для JS это означает работу со строками или `Decimal.js`; демо на Pyodide такой
проблемы не имеет — там значения не покидают Python.
