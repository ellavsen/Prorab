# ADR-006. Единица измерения заполняется, а подстановка объявляется

**Статус:** принято, Sprint 2. — **Отменено [ADR-015](ADR-015-spoken-units.md), Sprint 5.**

**Контекст.** Колонка `unit` существовала с самого начала, парсер умел вытащить
единицу из строки (`Побелка, 150 м2, 3000`) — и выбрасывал её, а в базу шла
пустая строка. При этом заголовок в Excel был захардкожен как
«Кол-во (м2/мп/шт)», то есть документ показывал заказчику единицу, которой в
данных не было. `money.md` §1.2 требует `unit` обязательным полем.

**Решение.**
1. Справочник канонических единиц и нормализация синонимов в
   `smeta_core.units` (`м2`→`м²`, `пм`→`м.п.`, `шт.`→`шт`, `ч`→`час`).
2. Распознанная единица сохраняется в `positions.unit`.
3. Если пользователь единицу не указал — подставляется по категории:
   `шт` для материалов, `м²` для работ. **Подстановка сообщается в ответе**
   («Единица не указана — поставила «шт» для: …»). Тихое домысливание данных
   недопустимо: это ровно тот класс поведения, из-за которого возникло ADR-005.
4. Незнакомая единица не является ошибкой ввода — она отбрасывается, и дальше
   работает подстановка по умолчанию. Отклонять `150 квадратов` целой строкой
   было бы хуже, чем принять количество и назвать единицу.
5. В XLSX появилась отдельная колонка «Ед.»; фальшивый заголовок убран. Пустая
   единица печатается как «—», но при вводе через бота она уже не встречается.

**Альтернативы.** Четвёртое поле ввода (`Наименование, ед, количество, цена`) —
ломает формат, к которому пользователь привык, и добавляет шаг на объекте.
Переспрашивать при каждой строке — превращает ввод десяти позиций в диалог.

**Следствия.** Формат ввода не изменился: единица по-прежнему берётся из поля
количества. Колонки формул в XLSX сдвинулись (`D`×`E` вместо `C`×`D`), тесты
паритета обновлены. Функция `default_unit` сравнивает категорию со строкой,
поэтому `Category` переведён на `StrEnum`: у `(str, Enum)` вызов
`str(Category.WORK)` даёт `"Category.WORK"`, и сравнение тихо не срабатывало.
