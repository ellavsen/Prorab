# Денежное ядро сметы: спецификация

Статус: проект (draft). Область: расчёт, округление, хранение и версионирование
смет в Telegram-боте «Прораб». Реализация — вне этого документа.

## 0. Диагноз текущего состояния

Сегодня итог считается четырьмя несовместимыми способами:

| Канал | Механика | Проблема |
|---|---|---|
| Python-итог (`sum_line_with_tax`) | `Decimal`, полная точность, без quantize | сумма не равна сумме отображённых строк |
| SQL-итог (`func.sum(... * (1 + float(TAX_RATE)))`) | binary float внутри SQLite | расходится с Decimal в копейках |
| Excel | `=C*D*1.06` — живая формула во float | расходится и с Python, и с отображением |
| Хранение | `Numeric(18,2)` в SQLite = аффинность NUMERIC → REAL | `0.1` уже хранится неточно; Decimal «восстанавливается» из float |

Целевой инвариант всего документа:

> **И1 (сходимость каналов).** Для одной и той же сметы Telegram-сообщение,
> XLSX (после пересчёта формул в Excel/LibreOffice) и PDF показывают
> побайтово одинаковые суммы строк и одинаковый итог, и итог равен
> арифметической сумме отображённых строк.

## 1. Доменная модель

### 1.1. Типы значений (value objects)

```
Money      = Decimal, ровно 2 знака после запятой (квантованный)
Quantity   = Decimal, до 3 знаков после запятой
Rate       = Decimal, процент, до 2 знаков после запятой (6.00 = 6%)
Category   = enum { WORK, MATERIAL }
Unit       = str из справочника (м², м³, шт, м.п., компл, т, кг, час, …)
```

Правила типов:

- **Деньги никогда не существуют как float.** float допустим в одном месте —
  при записи числа в ячейку XLSX (см. §3.4), и это значение обязано без потерь
  представлять исходный Decimal.
- **Хранение в SQLite — целые числа в минимальных единицах** (ADR-M1):
  `price_kop: int` (копейки), `qty_milli: int` (тысячные доли единицы),
  `rate_bp: int` (базисные пункты, 6.00% = 600). Конвертация в Decimal —
  только на границе репозитория. Это устраняет REAL-аффинность SQLite.

### 1.2. Сущности

**Estimate (смета)**

> Расхождение с кодом, оставленное сознательно: `id` здесь UUID, в реализации —
> INTEGER (SQLite, автоинкремент). Тип ключа не влияет ни на одно свойство,
> описанное ниже; менять схему ради совпадения со спецификацией — риск без
> выигрыша. То же про `owner_chat_id`: в коде он `user_id`.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `number` | int | человекочитаемый номер, уникален в паре с `version` в рамках владельца |
| `version` | int ≥ 1 | см. §1.4 |
| `supersedes_id` | UUID? | ссылка на предыдущую версию; NULL у v1 |
| `owner_chat_id` | int | владелец (Telegram chat) |
| `title` | str | |
| `status` | enum `DRAFT / SENT / SUPERSEDED / CANCELLED` | машина состояний §1.3 |
| `markup_work_rate` | Rate | наценка на работы, снимок на момент создания (§4) |
| `markup_material_rate` | Rate | наценка на материалы |
| `created_at`, `sent_at` | datetime | `sent_at` NULL до отправки |
| `rate_base` | enum `cost / price` | от чего берётся процент (§4.4) |
| `frozen_subtotal`, `frozen_markup`, `frozen_total` | Money? | снимок итогов, заполняется при `SENT` (§1.3) |
| `frozen_hash` | str? | SHA-256 канонической сериализации позиций + ставок при заморозке |
| `frozen_format` | int? | версия формата слепка; проверка идёт **ею**, а не текущей (§1.5) |

**Position (позиция сметы)**

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID | PK |
| `estimate_id` | UUID | FK, позиции живут только внутри сметы |
| `ord` | int | порядок отображения, стабилен |
| `category` | Category | |
| `name` | str | непустое, ≤ 200 символов |
| `unit` | Unit | **новое поле** — сейчас в модели отсутствует, хотя есть в вводе |
| `qty` | Quantity | `0 < qty ≤ 99 999.999`, не более 3 знаков |
| `price` | Money | `0 ≤ price ≤ 9 999 999.99` |

Границы qty/price — не декорация: они гарантируют «бюджет значащих цифр»
для точного паритета с Excel (§3.4).

Производные значения (никогда не хранятся у DRAFT, всегда считаются одной
функцией домена):

```
base(p)        = round2(p.qty × p.price)                  # сумма строки без наценки
line_total(p)  = round2(base(p) × (1 + rate(p.category))) # rate_base = cost
               = round2(base(p) / (1 − rate(p.category))) # rate_base = price, §4.4
subtotal       = Σ base(p)          # сумма уже квантованных значений
total          = Σ line_total(p)    # сумма уже квантованных значений
markup_amount  = total − subtotal   # ТОЛЬКО разностью, не умножением
```

### 1.3. Инварианты и машина состояний

```
DRAFT ──отправка заказчику──▶ SENT ──создание новой версии──▶ SUPERSEDED
  │                             │
  └─▶ CANCELLED                 └─▶ CANCELLED
```

- **И2 (изменяемость).** Позиции можно создавать/менять/удалять только при
  `status = DRAFT`. Переход в `SENT` необратим.
- **И3 (заморозка).** При переходе `DRAFT → SENT` в одной транзакции:
  вычисляются и записываются `frozen_*`, `frozen_hash`, `sent_at`.
  Любая последующая генерация документа по SENT-смете обязана перед выдачей
  сверить пересчитанный total с `frozen_total` и hash — расхождение это
  ошибка целостности (алгоритм менялся задним числом), документ не выдаётся.
- **И4 (защита в глубину).** Помимо проверки в домене — DB-триггер (или
  проверка в репозитории), запрещающий UPDATE/DELETE позиций сметы со
  статусом ≠ DRAFT. «Отправлено заказчику» = «по этому выставлен счёт»;
  тихое изменение недопустимо юридически.
- **И5 (агрегаты только в домене).** `func.sum` и любая денежная арифметика
  в SQL запрещены (ADR-M2). Итог DRAFT-сметы считается загрузкой строк;
  итог SENT-сметы читается из `frozen_total`.

### 1.4. Версионирование

Правка после отправки = **новая смета-версия**, не мутация:

1. `revise(estimate: SENT) → Estimate`: полная копия позиций и ставок,
   `number` тот же, `version + 1`, `supersedes_id → старая`, статус `DRAFT`.
   Старая версия получает `SUPERSEDED` **только когда новая уходит в SENT**
   (пока новая — черновик, действующей для заказчика остаётся старая).
2. Заказчику документ всегда подписывается как «Смета № {number}, ред. {version}
   от {sent_at}» — устраняет спор «какую смету вы мне присылали».
3. Уникальный индекс `(owner_chat_id, number, version)`.
4. Удаление версий запрещено; `CANCELLED` — мягкая пометка.

### 1.5. Формат слепка версионируется, а не правится

Хеш лежит в базах, до которых у нас доступа нет, и сверяется каждый раз, когда
заказчик открывает ссылку. Значит правка сериализации или арифметики обнуляет
**все** уже выданные документы разом: PDF и XLSX перестают выдаваться, а
публичная страница отвечает нейтральным 404 и по ADR-020 §3 не имеет права
назвать причину.

Поэтому смета помнит `frozen_format` и проверяется **им**, а не текущим
алгоритмом. Старые версии живут в коде и не переписываются.

- **Версия покрывает весь контракт заморозки — сериализацию и арифметику.**
  Правка округления расходится с `frozen_total`, не тронув хеш вовсе; версия
  только сериализации оставила бы этот путь открытым.
- **Старая версия — сверщик, а не калькулятор.** Она отвечает единственный
  вопрос «совпадает ли сохранённое с сохранённым» и недостижима из путей,
  которые считают новые числа; проверяется тестом архитектуры.
- **Версии не делят общего кода.** Вынесенный общий кусок означал бы, что
  правка ради следующего формата задним числом меняет предыдущий.
- **Отсутствие формата у замороженной сметы — отказ, а не догадка.** «Наверное,
  формат 1» — это тот же молчаливый дефолт, ради отказа от которого версии и
  заведены.

## 2. Единственный путь вычисления

Одна чистая функция — единственное место, где возникает денежная арифметика:

```python
def round2(x: Decimal) -> Decimal:
    """quantize(Decimal('0.01'), rounding=ROUND_HALF_UP)"""

def compute_totals(
    positions: Sequence[Position],
    markup_work_rate: Decimal,      # 6.00 означает 6%
    markup_material_rate: Decimal,
) -> EstimateTotals:
    """
    Для каждой позиции:
        factor = 1 + rate/100          # точный Decimal, ≤ 4 знаков
        base   = round2(qty * price)
        line   = round2(base * factor)
    Возвращает: строки (base, line), subtotal = Σbase,
    total = Σline, markup = total − subtotal.
    Никакой другой код не умножает деньги.
    """
```

SQL-слой, Telegram-рендер, XLSX-генератор и PDF-генератор — **потребители**
результата `compute_totals`, а не альтернативные вычислители.

## 3. Политика округления

### 3.1. Режим

`ROUND_HALF_UP` («математическое», 0.005 → 0.01). Причины:

- совпадает с ожиданием прораба и заказчика и с практикой первичных документов;
- для неотрицательных значений идентичен Excel-функции `ROUND`
  (half-away-from-zero) — а паритет с живыми формулами Excel является
  жёстким требованием. `ROUND_HALF_EVEN` этот паритет ломает.

Отрицательных денежных значений в домене нет (И-инварианты §1.2), поэтому
различие HALF_UP / half-away-from-zero недостижимо.

### 3.2. Где именно quantize (и где — нет)

| Точка | Действие |
|---|---|
| Парсинг ввода `price` | принять ≤ 2 знаков, иначе **отказ** с сообщением (не тихое округление) |
| Парсинг ввода `qty` | принять ≤ 3 знаков, иначе отказ (§5) |
| `base = qty × price` | `round2` — 1-е округление |
| `line = base × factor` | `round2` — 2-е округление |
| `subtotal`, `total` | суммирование уже квантованных — округления не требуется |
| `markup_amount` | `total − subtotal` — разность квантованных, точна по построению |
| Отображение | только форматирование (разряды, пробелы), **ни одного** нового округления |

Каскад из двух округлений — осознанное решение: он делает «сумму без наценки»
самостоятельной отображаемой величиной и резко сокращает разрядность
промежуточных чисел, что и обеспечивает точный паритет с Excel (§3.4).
Равенство «сумма отображённых строк = итог» выполняется **по построению**:
итог нигде не вычисляется иначе, чем суммой квантованных строк.

### 3.3. Каналы Telegram и PDF

Оба канала получают готовый `EstimateTotals` и одну общую функцию
форматирования `format_money(d: Money) -> str`. В шаблонах PDF и в тексте
сообщений арифметика запрещена (включая `sum(...)` по строкам в шаблоне —
итог берётся из `totals.total`). Тогда И1 для этих каналов тривиален.

### 3.4. XLSX с живыми формулами

Требование: заказчик открывает файл, видит формулы, Excel пересчитывает —
и получает те же копейки, что Python. Excel считает в IEEE-754 double,
поэтому наивная `=C2*D2*1.06` даёт расхождения. Решение — три правила.

**Правило A. Округление — внутри формулы, той же каскадной схемой.**

```
B1              : ставка работ, число 6.00 (или две ячейки для двух ставок)
E{r} (без нац.) : =ROUND(C{r}*D{r}, 2)
F{r} (с нац.)   : =ROUND(E{r}*(1+$B$1/100), 2)
F(итог)         : =SUM(F2:F{n})
E(итог)         : =SUM(E2:E{n})
Наценка итого   : =F(итог)-E(итог)
```

Итог — только `SUM` по округлённым ячейкам строк. Запрещено: формула итога
вида `=SUM(C:C*D:D)*1.06`, литерал ставки в формуле строки (ставка — одна
ячейка, на которую ссылаются формулы; правка ячейки заказчиком меняет итог
честно и на виду).

**Правило B. Записываемые значения обязаны точно представляться в double
на 15 значащих цифрах.**

Почему это работает: `ROUND` в Excel — не float-округление, а округление
15-значного десятичного представления числа (эмпирически:
`=ROUND(2.675, 2) → 2.68`, хотя double(2.675) < 2.675). Значит, если точное
десятичное значение произведения укладывается в ≤ 15 значащих цифр, Excel
округлит именно его — так же, как Decimal с HALF_UP. Бюджет цифр:

- `qty` ≤ 3 зн. после запятой, ≤ 99 999.999 → ≤ 8 значащих цифр;
- `price` ≤ 2 зн., ≤ 9 999 999.99 → ≤ 9 значащих цифр;
- `qty × price` → ≤ 5 знаков после запятой, величина < 10¹² → ≤ 15 значащих цифр ✓
- `E{r}` — уже деньги (2 знака), `× (1 + rate/100)` (фактор ≤ 4 знаков) →
  ≤ 6 знаков после запятой, < 10¹³ → ≤ 15 значащих цифр при line < 10⁹ ✓

Отсюда ограничения §1.2 на qty/price — они входят в контракт домена именно
ради этого бюджета, а каскад двух `ROUND` не даёт разрядности выйти за 15
цифр даже на больших сметах.

**Правило C. Паритет проверяется тестами, а не верой.**

- юнит-эмулятор `excel_round(x: float, nd: int)` (15-значное десятичное
  представление double → half-away-from-zero), property-тест
  `excel_round(float(qty*price)) == python-путь` на всём домене входов;
- интеграционный тест в CI: сгенерировать XLSX, пересчитать headless
  LibreOffice (`--convert-to`), сравнить значения ячеек с `frozen_total`.

Записывать в ячейки C/D следует `float(qty)`, `float(price)` — по бюджету
цифр это без потерь; писать строки нельзя (сломаются формулы у заказчика).

### 3.5. Деление: вторая формула строки

Всё выше посчитано для умножения. Когда процент берётся от суммы заказчику
(§4.4), строка получается делением, и правило B к нему не применимо: частное
`base / (1 − r/100)` в общем случае **конечной десятичной записи не имеет**,
поэтому «уложиться в 15 значащих цифр» нельзя даже в принципе. Совпадение
Decimal с Excel здесь — отдельное свойство, а не следствие §3.4.

```
F{r} (без нац.) : =ROUND(C{r}*D{r}, 2)
G{r} (с нац.)   : =ROUND(F{r}/(1-$B$1/100), 2)
```

**Правило D. Python делит тем же делением, а не умножает на обратное.**
`1/0,94` в `Decimal` — это 28 значащих цифр, и `base × (1/0,94)` есть другая
операция, которая с `base / 0,94` совпадает по совпадению, а не по правилу.
В коде стоит деление, буквально повторяющее формулу ячейки.

**Правило E. Ставка при этом основании ограничена 50%.** Множитель `1/(1−r)`
растёт неограниченно: 50% → ×2, 90% → ×10, 99,99% → ×10 000, 100% → деление
на ноль. Половина удерживает его в тех же ×2, под которые посчитан бюджет
§3.4; выше паритет не проверялся, и домен отказывает. Наценке сверху этот
потолок не нужен — её множитель не превышает ×1,9999 при `RATE_MAX`.

**Замер.** Развёртка Decimal против эмулятора `excel_round`: 4,4 млн строк на
11 ставках от 1% до 50% плюс крупные базы около 99 млн — ноль расхождений.
В CI это property-тест `test_c8_excel_parity_when_the_percent_comes_off_the_sum`,
а не разовый прогон.

**Чего деление не сохраняет.** «Удержанное = процент от выставленного» верно
**на строке** и неверно **на смете**: после построчного округления сумма
удержаний перестаёт быть процентом от итога. Замер: 20 000 случайных смет по
20–120 строк, равенство нарушено в 81,4% случаев, максимум расхождения 13
копеек. Поэтому `markup_amount` остаётся разностью (§3.2), и ни один документ
не предлагает проверить его умножением.

## 4. Наценка

### 4.1. Почему на уровне сметы, а не глобально

1. **Историческая корректность.** Глобальная константа задним числом меняет
   уже отправленные сметы — прямое нарушение И3 и юридический риск: счёт
   выставлен на одну сумму, пересчёт даёт другую. Ставка — часть документа.
2. **Коммерческая реальность.** Наценка — переговорная величина: для разных
   заказчиков и объектов разная. Глобальная ставка заставляет менять
   «настройку всего бота» перед каждой сметой.
3. **Прозрачность.** Ставка на смете попадает в документ (ячейка B1 в XLSX,
   строка в PDF) — заказчик видит, из чего сложился итог; «зашитый» 1.06
   в формуле выглядит как скрытая накрутка.

### 4.2. Модель: две ставки

`markup_work_rate` и `markup_material_rate` — раздельно. Основание: в
строительной практике наценка на материалы (снабжение) и на работы —
разные величины и часто торгуются отдельно. Единая ставка — частный случай
(две равные), обратное неверно; при этом схема расчёта (§2) от количества
ставок не усложняется — ставка выбирается по `category` строки.

Значения по умолчанию для **новых** смет берутся из настроек владельца
(`default_markup_work_rate`, `default_markup_material_rate`); при создании
сметы значение **копируется** в неё (снимок). Диапазон: `0.00 ≤ rate ≤ 99.99`,
шаг 0.01 процентного пункта.

### 4.3. Смена ставки и исторические сметы

- Изменение настроек владельца влияет только на сметы, созданные после.
- В DRAFT ставку можно править явной командой — пересчитывается весь черновик.
- В SENT ставка неизменяема (И2/И3). Нужна другая ставка — `revise()` → новая
  версия (§1.4).

### 4.4. Основание: от чего берётся процент

Слово «6%» неоднозначно, и неоднозначно в нём именно основание:

```
от цены исполнителя  250 × 1,06        = 265,00
от суммы заказчику   250 / (1 − 0,06)  = 265,96
```

Второе — не наценка прораба, а **условие договора с заказчиком**: процент
удерживается из выставленной суммы, поэтому её тянут вверх, чтобы исполнитель
получил ровно свою цену. Найдено на настоящей смете; при умножении на 1,06
исполнитель недополучает с каждой строки около 0,4% своей цены, всегда в одну
сторону.

`rate_base ∈ {cost, price}` — **поле сметы, а не строки**: договор один на
документ. Ставок при этом по-прежнему две (§4.2): договор вполне может
удерживать процент с работ и возмещать материалы по счёту.

Границы: `cost` — до `RATE_MAX`, `price` — до 50% (§3.5, правило E).
- Миграция существующих данных: всем существующим сметам проставить
  `6.00 / 6.00` (текущая константа), после чего `TAX_RATE` удалить.
  Имя «TAX» ложное — это не налог; в домене термин ровно один: «наценка»
  (markup). Если позже появится настоящий НДС, это отдельное поле с
  отдельной семантикой, а не переиспользование ставки.

## 5. Количество (qty)

- Точность ввода: **до 3 знаков после запятой** (40.5 м²; 1.125 м³).
  Хватает для всех практических единиц (м², м³, м.п., т); 3 знака = хранение
  в целых тысячных (`qty_milli`).
- Ввод с 4+ знаками — **отказ с подсказкой**, не тихое округление: прораб
  должен сам решить, 12.3456 → 12.346 или 12.35. Тихое округление на вводе —
  источник «у меня в блокноте другая цифра».
- Запятая как десятичный разделитель принимается и нормализуется в точку.
- `qty > 0`; нулевые и отрицательные количества запрещены (позиция без
  количества — не позиция).
- Влияние на итог: qty участвует ровно в одном умножении `qty × price`,
  результат немедленно квантуется до копеек (§3.2), дальше qty на итог
  не влияет. Точное произведение имеет ≤ 5 десятичных знаков — округляется
  предсказуемо и одинаково в Python и Excel (§3.4).
- Слияние дублей (существующее поведение «та же позиция — прибавить qty»)
  обязано проверять переполнение лимита 99 999.999 и выполняться до расчёта.

## 7. ADR (краткие фиксации)

### ADR-M1. Деньги и количества хранятся целыми в минимальных единицах

**Решение.** В SQLite: `price_kop INTEGER`, `qty_milli INTEGER`,
`rate_bp INTEGER`; в домене — `Decimal`; float в домене запрещён.
**Контекст.** SQLite не имеет точного десятичного типа: `Numeric(18,2)`
хранится как REAL, т.е. деньги уже сейчас лежат в binary float.
**Альтернативы.** TEXT-хранение Decimal (теряем сортировку/сравнение в SQL);
смена СУБД (несоразмерно задаче).
**Следствия.** Конвертация строго на границе репозитория; тест C9 —
round-trip без потерь; сравнения и лимиты в SQL остаются честными.

### ADR-M2. Единственный вычислитель итогов — чистая функция домена

**Решение.** Вся денежная арифметика — в `compute_totals` (§2). SQL-агрегаты
по деньгам запрещены (линтер-правило/ревью: `func.sum` на денежных колонках —
ошибка). XLSX-формулы — не второй вычислитель, а транскрипция той же схемы,
паритет которой доказывается тестами E1–E3 и C8. Итоги SENT-смет читаются
из замороженного снимка.
**Контекст.** Три параллельных пути расчёта уже разошлись в копейках.
**Альтернативы.** «Синхронизировать» три пути дисциплиной — не работает,
что и наблюдаем.
**Следствия.** Итог по большим сметам требует загрузки строк — при наших
размерах (сотни строк) несущественно; для SENT — O(1) из снимка.

### ADR-M3. Округление ROUND_HALF_UP, per-line, двухкаскадное; смета после отправки неизменяема

**Решение.** Каждая строка округляется до копеек дважды (база, затем база
с наценкой); итоги — только суммы округлённых строк; режим HALF_UP.
Отправленная смета — юридический документ: заморожена со снимком итогов
и хешем; правки — только новой версией с видимым номером редакции.
**Контекст.** Требование И1 (три канала, включая живые формулы Excel,
считающего во float) выполнимо только при округлении на уровне строки:
Excel-`ROUND` совпадает с HALF_UP на неотрицательных числах, а каскад
удерживает разрядность в 15 значащих цифрах double.
**Альтернативы.** HALF_EVEN (ломает паритет с Excel-`ROUND`); округление
только итога (сумма строк на экране ≠ итог); XLSX со «вбитыми» значениями
вместо формул (заказчики требуют проверяемые формулы).
**Следствия.** Семантика «Σ построчных копеек», зафиксированная тестом B5:
итог может отличаться от «идеального» непрерывного расчёта — это цена
сходимости всех каналов и она принята.

## 8. Явно вне области

- Мультивалютность (валюта одна, рубль; поле не заводим — YAGNI).
- НДС и налоги (наценка ≠ налог; появится — отдельным полем и отдельным ADR).
- Скидки/отрицательные строки (запрещены инвариантами; отдельная фича).
