# СМЕТА → «Прораб»: мастер-план пересборки и пакет промптов

Документ на входе: аудит проекта «Смета» (Telegram-бот для строительных смет).
Задача на выходе: публичный GitHub-проект, который можно «пощупать», с живым демо, тестами и внятной продуктовой историей.

---

## 0. Стратегическое решение (читать первым)

### 0.1. Главный тезис

Аудит говорит: «инженерия хорошая, ИИ нет — вкладывайтесь в интеллект».
Это верно, но **буквально следовать этому опасно**. Если навесить LLM поверх всего, получится ещё один «бот с ИИ», а сильная сторона проекта (аккуратные деньги) утонет.

Правильная формула проекта — и она же слоган для README:

> **LLM превращает речь, фото и текст в структуру. Деньги считает код.**

ИИ живёт **только на границе ввода**. Ядро расчёта остаётся детерминированным, покрытым тестами и полностью проверяемым. Это ровно то, что отличает «инвестиционный» инженерный проект от демки: понимание, где машинному обучению не место.

### 0.2. Три сильные стороны из аудита, которые мы усиливаем

| Что есть сейчас | Во что превращаем | Зачем это инвестору/рекрутёру |
|---|---|---|
| Деньги в `Decimal` | Отдельный пакет `smeta-core` — финансовое ядро, 100% покрытие тестами, документированная политика округления | Показывает финансовую дисциплину и умение изолировать домен |
| Excel с живыми формулами | Экспорт-движок: XLSX + PDF + публичная веб-ссылка на смету | Осязаемый артефакт, который прораб отдаёт заказчику |
| Реальная миграция схемы + мульти-сметы | Версионирование смет: v1/v2, дифф «что изменилось», статус «согласовано» | Превращает утилиту в документооборот — это уже продукт |

### 0.3. Что убиваем без сожаления

- монолит `main_agent.py` на 856 строк;
- колонка `unit`-призрак (либо заполняем, либо удаляем — компромисса нет);
- недостижимая ветка `else: await handle_category(...)`, ветки `del:`/`edit:` без кнопок;
- глобальные dict'ы `user_category`, `current_estimate_cache`;
- три расходящихся пути расчёта суммы;
- `.venv`, `estimate.db`, `estimate_<user_id>_*.xlsx`, дубль `env` — из репозитория;
- строковая интерполяция SQL в `enforce_retention`.

### 0.4. Одна killer-фича, а не двенадцать

Roadmap аудита содержит 12 пунктов. Реализовать все — значит не доделать ни одного.
**Выбираем одну историю и вокруг неё строим всё:**

> Прораб стоит на объекте, руки в цементе, телефон в кармане. Он нажимает кнопку и говорит:
> «Стяжка сорок квадратов по семьсот, двадцать мешков цемента по триста пятьдесят».
> Через пять секунд у заказчика в почте Excel со сметой и PDF с подписью.

Всё остальное (справочник цен, версии, PDF) — обслуживает эту историю.

### 0.5. Идея мониторинга рынка цен

Это не фича бота, а **отдельный сервис `price-radar`** — и стратегически самая ценная часть проекта, потому что это единственный компонент, создающий **данные**, которых нет у конкурентов. Данные = защитный ров.

Роль в проекте тройная:
1. **Продуктовая**: подсказка цены при вводе позиции («цемент М500 — медиана 372 ₽/мешок по 14 источникам за 30 дней»).
2. **Контентная**: еженедельный дайджест «Индекс цен» в канал → бесплатный привлекающий канал.
3. **Инвестиционная**: единственный компонент с сетевым эффектом.

**Честно о рисках (я не юрист, проверьте под свою юрисдикцию):**
- Массовый парсинг Telegram через user-аккаунт (Telethon) — серая зона по ToS и риск бана аккаунта.
- В сообщениях чатов есть персональные данные (телефоны, имена) — хранить их нельзя.

**Безопасная архитектура, которую и закладываем:**
- источники — только **публичные каналы**, добавляемые пользователем явно (opt-in, список в конфиге/БД);
- хранится **не текст сообщения**, а извлечённый факт: `{материал, цена, единица, регион, дата, ссылка_на_источник}`;
- второй источник — **ручной ввод цен самими пользователями** (краудсорсинг: «подтвердить цену / предложить свою»);
- третий — открытые прайс-листы поставщиков (HTML/XLSX по прямым ссылкам);
- ни одного персонального данного в БД, только агрегаты.

Начинать с краудсорсинга + открытых прайсов, парсинг каналов добавлять как опциональный модуль. Это и юридически чище, и в презентации звучит лучше.

### 0.6. Название и позиционирование

`smeta` — не гуглится и ничего не говорит. Варианты для репозитория:

- **`prorab`** — «AI-сметчик в кармане прораба» (моё предпочтение: короткое, произносимое, точно в аудиторию);
- `smeta-ai`;
- `estimate-radar` (если делать акцент на ценах).

Слоган для README: *«Смета голосом. За 30 секунд. С объекта.»*

## 2. Как сделать, чтобы проект можно было «пощупать»

Четыре уровня доступа — от «посмотреть за 5 секунд» до «запустить у себя».

### Уровень 1 — README (5 секунд)
Бейджи CI/coverage, GIF с записью диалога с ботом, mermaid-схема архитектуры, три ссылки: демо / бот / документация.

### Уровень 2 — GitHub Pages (30 секунд, без регистрации) ⭐ главное
`apps/web` — Vite + React, деплой через GitHub Actions на Pages. Два режима:
- **DEMO** (по умолчанию): всё живёт в браузере, seed-смета «Санузел 4 м²», расчёт через WASM/JS-порт логики или через мок; **экспорт XLSX прямо в браузере через SheetJS** — человек скачивает настоящий файл, не выходя со страницы.
- **LIVE**: если задан `VITE_API_URL` — фронт стучится в реальный API.

Это ключевой пункт: посетитель нажимает «Попробовать», добавляет позицию голосом или текстом, видит смету и скачивает Excel. Без бэкенда, без ключей, без cold start.

### Уровень 3 — живой бэкенд
FastAPI в Docker на **Hugging Face Spaces** (бесплатно, Docker SDK) или Railway/Render. Даёт LIVE-режим фронту и `/docs` со Swagger — отдельный плюс к впечатлению.

### Уровень 4 — запуск у себя
`docker compose up` поднимает бота + API + веб. **Обязательно: без единого ключа проект должен стартовать в DEMO-режиме** (стаб LLM возвращает заранее записанные ответы). Рекрутёр не будет заводить токен Telegram.

В Telegram-боте — команда `/demo`: генерирует пример сметы и присылает Excel, чтобы можно было оценить продукт без ввода данных.

## 3. План спринтов

Формат каждого: цель → артефакты → критерий готовности (DoD) → модель.

| # | Спринт | Модель | Оценка |
|---|---|---|---|
| 0 | Гигиена и безопасность (P0) | Opus 5 | 0.5 дня |
| 1 | Финансовое ядро `smeta-core` + тесты | **Fable** (дизайн) → Opus (код) | 2 дня |
| 2 | Разбор монолита, storage, устранение мёртвого кода | Opus 5 | 2 дня |
| 3 | FastAPI + web-демо + GitHub Pages | Opus 5 | 2–3 дня |
| 4 | UX ввода: парсер, единицы, настраиваемая наценка | Opus 5 | 1–2 дня |
| 5 | AI-слой: голос → смета | **Fable** (промпты+eval) → Opus (код) | 3 дня |
| 6 | `price-radar` | **Fable** (схема данных) → Opus (код) | 3 дня |
| 7 | PDF, публичная ссылка на смету, версии, согласование | Opus 5 | 2 дня |
| 8 | Упаковка: README, docs, GIF, лицензия, релиз | Opus 5 + **Fable** (финальное ревью) | 1 день |

### Sprint 0 — Гигиена (делать прямо сегодня)
1. **Ротировать токен через @BotFather немедленно** — он уже утёк в два файла.
2. Удалить `env`, добавить `.gitignore` (`.venv/`, `*.db`, `*.xlsx`, `.env`, `__pycache__/`).
3. Если репозиторий уже был запушен с БД/токеном — история переписывается (`git filter-repo`) или создаётся чистый репозиторий с нуля. **Не оставляйте реальные `user_id` в истории.**
4. `html.escape()` на все пользовательские строки в сообщениях.
5. Заменить строковый SQL в `enforce_retention` на `.in_()`.
6. Добавить `.env.example`, `LICENSE` (MIT), `README.md`-заглушку.

**DoD:** `git log -p | grep -i token` ничего не находит; позиция «Уголок <30мм> & крепёж» не роняет `/list`.

### Sprint 1 — Финансовое ядро
Самый важный спринт для впечатления «этому человеку можно доверить деньги».

Принципы, которые фиксируем в `docs/money.md`:
- всё в `Decimal`, `float` запрещён на всём пути (линтер-правило);
- округление **на каждой строке**: `(qty * price).quantize(Decimal("0.01"), ROUND_HALF_UP)`;
- итог = сумма **уже округлённых** строк. Тогда «сумма на экране = сумма в Excel» до копейки;
- **наценка хранится в самой смете, а не в глобальной константе.** Смета — документ; изменение глобальной ставки не должно менять уже выставленную смету;
- одна функция `calculate_estimate()` — единственный источник истины. `/list`, `/estimates`, XLSX и PDF вызывают её и только её.

**DoD:** property-тест на 10 000 случайных смет: `sum(строк в UI) == итог в /estimates == итог в Excel`. Тесты на парсинг, слияние дублей, миграцию.

### Sprint 2 — Разбор монолита
Механическая, но обязательная работа. `main_agent.py` → пакеты. Мёртвый код удалён. Состояние переезжает из dict'ов в БД (таблица `user_state`). `unit` — решение принято и реализовано.

**DoD:** ни один файл длиннее 300 строк; рестарт процесса не теряет активную смету; `vulture`/`ruff` не находят мёртвого кода.

### Sprint 3 — API и демо
FastAPI поверх core, OpenAPI-схема, React-фронт, GitHub Actions на Pages.

**DoD:** демо открывается по публичной ссылке и позволяет собрать смету и скачать XLSX без бэкенда.

### Sprint 4 — UX ввода
Пошаговый ввод как основной путь (кнопки, а не CSV), свободный формат как быстрый. Единицы измерения. `/rate 6`. Устойчивый парсер (запятая внутри имени больше не ломает).

### Sprint 5 — AI-слой (killer-фича)
- голосовое сообщение → Whisper/ASR → текст → LLM-извлечение → **предпросмотр с подтверждением** (LLM никогда не пишет в смету напрямую);
- фото накладной → OCR → позиции → тот же предпросмотр;
- свободный текст → те же позиции;
- провайдер-агностичный интерфейс `AIProvider` + `StubProvider` для тестов и DEMO-режима;
- eval-набор: 40–60 размеченных примеров, метрика — доля корректно извлечённых позиций.

**DoD:** eval прогоняется в CI; демо работает без ключей на стабе.

### Sprint 6 — price-radar
Схема факта цены, нормализация названий материалов, дедупликация, отсев выбросов (медиана + IQR), агрегация по региону и периоду, API `/prices/suggest?name=...`.

**DoD:** по названию «цемент м500» возвращается медиана, разброс и число источников; в БД нет ни одного персонального данного.

### Sprint 7 — Документооборот
PDF, публичная ссылка на смету (`/e/{token}`), версии, статус «согласовано».

### Sprint 8 — Упаковка
README с историей, GIF, архитектурной схемой; `docs/`; релиз v1.0.0; закреплённый репозиторий в профиле GitHub.

## 4. Как потратить $100 на Fable и не разориться

**Правило:** Fable думает, Opus печатает.

Генерация кода — самая объёмная по токенам часть, и она отлично делается Opus 5 в Claude Code по подписке. Fable вызывается **сессиями по конкретному вопросу**, где цена ошибки высока и переделка дороже.

| Сессия Fable | Что просим | Ориентир бюджета |
|---|---|---|
| F1. Дизайн денежного ядра | Доменная модель, политика округления, список из ~40 тестов. **Без кода** — спецификация и тест-план | ~$10 |
| F2. AI-извлечение позиций | Системный промпт, JSON-схема, обработка неоднозначностей, eval-набор | ~$25 |
| F3. Схема price-radar | Модель факта цены, нормализация названий, антивыбросы, юридически безопасный дизайн | ~$20 |
| F4. Ревью архитектуры (после Sprint 3) | Взгляд со стороны: что сломается при росте | ~$15 |
| F5. Финальное ревью «глазами инвестора» | Что мешает поверить в проект | ~$15 |
| Резерв | | ~$15 |

**Как экономить токены на Fable:**
1. Не давайте ему репозиторий целиком. Готовьте выжимку: интерфейсы, сигнатуры, схему БД, конкретный вопрос.
2. Просите **решение и план**, а не тысячи строк кода. Одна страница архитектурного решения стоит копейки и экономит два дня.
3. Один вопрос — одна сессия. Не тяните длинный диалог: каждый следующий ответ оплачивает всю предыдущую переписку.
4. Ответ Fable сохраняйте в `docs/decisions/ADR-00X.md` и передавайте Opus как вводную. Это ещё и красиво смотрится в репозитории (Architecture Decision Records).

**Отдельно про runtime-стоимость:** $100 — это бюджет разработки, не эксплуатации. Для извлечения позиций в проде берите самую дешёвую модель (Haiku-класс) — задача простая, структурированная. Заложите лимит вызовов на пользователя в день.

### Промпт C — для Fable, сессия F1: денежное ядро

```
Роль: главный инженер финансового ПО. Задача — спроектировать (НЕ кодировать)
доменное ядро для расчёта строительных смет.

КОНТЕКСТ
Telegram-бот для прорабов. Пользователь вводит позиции: наименование, количество,
цена за единицу, категория (Работа/Материал), единица измерения. Смета —
это документ, который отдаётся заказчику и по которому выставляется счёт.

ТЕКУЩАЯ ПРОБЛЕМА
Итог считается тремя разными путями и расходится в копейках:
1. Decimal в Python: sum(qty * price * Decimal("1.06"))
2. float в SQLite: func.sum((qty * price) * (1 + float(TAX_RATE)))
3. float при генерации Excel: float(qty) * float(price) * 1.06
Округления нет: строки отображаются как .2f, а суммируется полная точность,
поэтому сумма строк на экране не совпадает с итогом.
Наценка 6% зашита константой, назначение не определено.

ЧТО НУЖНО ОТ ТЕБЯ (спецификация, без реализации)
1. Доменная модель: сущности, поля, типы, инварианты. Явно опиши, что делает
   смету неизменяемой после отправки заказчику и как устроено версионирование.
2. Политика округления: где именно quantize, какой режим, как гарантировать
   равенство «сумма отображённых строк = итог» во всех трёх каналах
   (Telegram-сообщение, XLSX с живыми формулами, PDF).
   Отдельно: как сделать так, чтобы формулы Excel (=C*D*(1+rate)) давали
   тот же результат, что и Python — с учётом того, что Excel считает во float.
3. Наценка: аргументируй хранение на уровне сметы, а не глобально. Опиши модель:
   одна ставка на смету или разные на работы и материалы? Как быть с историческими
   сметами при смене ставки?
4. Количество: qty может быть дробным (40.5 м²). Какая точность допустима,
   где округляется, как это влияет на итог.
5. Тест-план: список из 30–50 конкретных тестов с ожидаемым поведением, включая
   property-based тесты и граничные случаи (нулевая цена, огромные числа,
   0.005 на границе округления, отрицательные значения).
6. Три архитектурных решения, которые ты бы зафиксировал в ADR, с обоснованием.

ФОРМАТ ОТВЕТА
Markdown-спецификация, готовая к сохранению как docs/money.md.
Код только в виде сигнатур функций и псевдокода. Без реализации.
```

### Промпт D — для Fable, сессия F2: AI-извлечение позиций

```

позиций сметы из естественного языка.

Прораб на объекте отправляет голосовое сообщение боту. ASR даёт сырой текст,
```
